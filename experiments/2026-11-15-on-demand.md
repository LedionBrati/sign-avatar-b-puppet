# 2026-11-15: generate-on-use (missing signs rendered in the background)

**Who:** Nikos (with Claude)
**Question:** when a sentence needs a sign we have motion for but no realistic clip yet, can the server make that clip by itself in the background, and how long until the sign is usable?
**Why it matters:** we have ~400 extracted signs but only 34 realistic clips. Pre-rendering everything costs money up front. This only pays for signs people actually use.

## Design
- **Trigger:** after `/api/sign` has its gated plan, the server re-plans the text (rules only) against clips + motion-only signs (`MOTION_DIRS`). Words that need a sign with motion but **no clip** are queued (deduped, `out/ondemand/state.json`). The agent's `not_in_vocab` ids count too, if they have motion. Words with no motion stay plain `unsupported`.
- **The request is not delayed.** It returns what the safety gate allows now (caption-only when a sign is missing) plus `generating: [{motion_id, gloss, eta_s}]`. Web Live, the extension overlay and mobile Live show a chip: "Generating HAPPY, FOOD… ~3 min".
- **Worker:** one, in-process, one batch at a time. It waits ~3 s so a sentence's signs share a batch, then:
  1. Builds `NEUTRAL S1 NEUTRAL S2 … NEUTRAL` with `puppet/compose.mjs`, padded with a neutral hold to ≥ 5 s and split above 14 s. Every cut point needs ≥ 3 still neutral frames.
  2. Renders it with `puppet/render.mjs --view vrm`.
  3. Repaints it with H3 Max Recast (768P, safety checker on, input shape from `pipeline/e0/models.mjs`) through `pipeline/lib/fal.mjs`.
  4. Checks output frames == input frames.
  5. Cuts it with `cutClips` (the `sign-clips.mjs cut` logic, moved to `pipeline/lib/clips.mjs`) into `out/realtime/clips-ondemand/` (its own manifest).
  6. **Hot-reloads** the clip library and vocab. No restart.
- **Failures:** a failed batch is retried once. After that the sign is `failed` with a code and reason (for example `frames_mismatch`) and stays caption-only. The server never crashes. Errors are redacted.
- **Spend controls:**
  - Off by default. It needs `ONDEMAND=on`, a fal key (`FAL_KEY_FILE`) and `MOTION_DIRS`.
  - `FAL_DAILY_BUDGET_USD` (default 20) caps a per-batch **reserve** of $0.25 per video second (min 5 s). A batch that would go over is refused before any fal call. Nothing is queued once even a 5 s batch no longer fits.
  - `ONDEMAND_MAX_QUEUE` (default 30) caps the queue.
  - Status: `GET /api/ondemand`; `health.ondemand`.
- **Key:** read from the file at startup and set as `FAL_KEY` inside the server process only. The compose/render child processes get an environment without it. Every stored or logged error goes through the redactor. A scan of the worktree, logs, state and git history found no copy of the key.

## Setup (live test, one paid batch)
- Test server on :8796, CPU only:

  ```bash
  ONDEMAND=on FAL_KEY_FILE=<path-to>/fal-key.txt FAL_DAILY_BUDGET_USD=3 \
    CLIPS_DIR=<main-checkout>/out/realtime/clips MOTION_DIRS=<motion-checkout>/out/motion/wlasl \
    PUPPET_RENDER=<puppet-checkout>/puppet/render.mjs AGENT=off SEMANTIC=0 PORT=8796 node app/server/index.mjs
  ```

- 403 signs with motion passed QC; 34 had clips.
- Sentence: **"I am happy. I want food."** I and WANT have clips. HAPPY (95.7 % hand detection) and FOOD (97.1 %) have motion only.

## Result
- **First request:** `caption_only`, empty playlist, `unsupported: [happy, food]`, `generating: [HAPPY, FOOD]` with `eta_s: 163`. The response took 8.5 ms in total: queueing adds nothing noticeable.
- **One batch:** `od-20261115T055642-91z6`, HAPPY + FOOD, 122 frames (5.08 s, padded to the 5 s minimum). Recast request `01a1ddc8-2bcf-7e80-8e53-9451d3b01122`.
- **Frames in == out:** 122 → 122, 768×1024, same encoding as the existing clips. HAPPY is 47 frames, FOOD 49.

| Step | Time |
|---|---|
| queued → batch start (gather) | 3.0 s |
| compose | 0.27 s |
| puppet render (CPU, 0.30 s/frame) | 36.9 s |
| fal: upload + Recast + download (Recast alone: 78 s) | 83.6 s |
| frame check + cut 2 clips | 3.3 s |
| hot reload | 0.01 s |
| **queued → available** | **127 s (~2.1 min)** |

- **Next request,** same sentence, no restart: `fully_supported`, playlist `I HAPPY I WANT FOOD`, 5.3 ms. `/api/sign.mp4` joined it in 0.33 s. On the contact sheet the new clips match the old ones: same avatar, same neutral pose.
- **Cost:** a reserve of **$1.27** was counted against the budget. The listed H3 Max price for 5.08 s is ~$0.43, about $1.12 with input tokens. Check the fal dashboard for the real number.
- **ETA:** estimated 163 s; actual 127 s. The worker now learns the rate from finished batches: 23.7 s of wall time per video second here.

  - the key is never in status, state, logs or the child env
- All 45 existing server tests still pass (52 total).

## Limits
- **First use of a sign** = captions plus a ~2–3 min wait. **Later uses are instant.** With a longer queue, later batches wait (one at a time; ~2 min per 5 s batch, more for longer batches).
- Quality is whatever the WLASL motion + puppet gives. Nobody reviews a generated clip before it goes live. The 80 % hand-detection bar and the safety checker are the only gates. A signer should spot-check `out/realtime/clips-ondemand/`.
- The motion `gloss` becomes the clip gloss. Senses are not checked: one WLASL video per gloss, same as the offline vocab.
- A batch that fails after the fal call costs money, and its retry costs it again (the budget still caps it).
- The puppet render is CPU-bound on this laptop. It runs in a child process, but the server shares the machine while it renders.

## What I'd try next
- Pre-warm: queue the top-N most frequent words from real sessions overnight, under a separate budget.
- A signer review flag for generated clips (play them, but mark them "unreviewed" in the UI).
- Batch smarter: fill a batch up to ~10 s with queued signs to cut the per-batch overhead (the 5 s minimum wastes ~1 s of padding for 1–2 signs).
